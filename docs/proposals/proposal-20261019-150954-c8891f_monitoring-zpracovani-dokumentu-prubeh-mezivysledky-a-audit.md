# Monitoring zpracování dokumentů — průběh, mezivýsledky a audit

## Záměr <!-- section:intent type:context -->
Operátor má u dokumentu zjistit **kde právě je, co už vzniklo, co selhalo, co se opakuje a ze kterého běhu pochází zobrazený výsledek**. Ne další log viewer ani druhý scheduler. **Dodáváme pouze API pro budoucí konzumenty; žádné UI ani backoffice obrazovky.** Audit implementujeme jako interní Python package uvnitř stávající služby `be-document-processing`, bez nové aplikace, root modulu, procesu či deploy jednotky. **Současná business data a jejich úložiště zůstanou přesně jak jsou. Audit ukládá runtime události navázané jejich identifikátory, nikoli kopie dokumentu, uploadu nebo analýzy.** Velké business výsledky zůstávají v existujícím S3, malý append-only runtime deník v odděleném úložišti. Běh, pokus, krok a průběh jsou čtecí pohledy nad událostmi, nikoli nové business entity k samostatnému zapisování. Tato revize upravuje pouze návrh. Sama nespouští implementaci, deploy, inference ani zpracování existujících dokumentů; budoucí dodávka každého slice zahrnuje instalaci, nasazení do existujícího AWS test prostředí a skutečné API E2E podle projektového `AGENTS.md`.

## Ověřený základ a identity <!-- section:source-contract type:context -->
### Co skutečně existuje
Zdrojový modul `be-document-processing` má upload → ověření souboru/verze/hash → frontu → stránkový native/vision přepis → samostatnou extrakci a ověření důkazů → výsledek. Ukládá stránkové cache, náhledy, výsledky a audit oprav. Job má běh, pokusy a owner/lease; opakování nemusí vytvořit nový běh. `auto` rozhoduje pro každou stránku zvlášť, `visual` vynucuje vision. Úspěšné stránky se znovu použijí z cache, selhané zůstanou ve výsledku jako selhané. Následná deterministická validace případu porovnává doložené hodnoty napříč dokumenty a je dnes volaná při čtení, nikoli samostatná potvrzená worker stage.

**AWS má odlišný kontrakt než tento adapter.** Existující `wonderfulkb-uw-documents` a `wonderfulkb-uw-document-analysis` mají klíče `(case_id, document_id)`. První eviduje přijetí a S3 originál; druhá aktuální analýzu, štítek, stav, počet stran a odkaz na text. Zdrojový `AwsRepository` očekává `pk/sk/payload/revision` a SAM pro něj definuje jinou tabulku. Nesmí se pouze změnit název tabulky v konfiguraci. Inventura vybraného AWS účtu/regionu neprokázala běžící processing SAM/Lambda/SQS; existující analýzy tedy nelze bez další provenance připsat tomuto workeru.

### Rozhodnutí
- **Aktuální AWS business schéma má přednost před starším kódem komponenty.** Dnešní atributy jsou výchozí evidence, ne zamrazený požadavek na budoucí DB. Zadání implementace formulovat podle entit a chování; agent před prací ověří aktuální strukturu/ownery a přizpůsobí mapování. Žádná migrace AWS do pk/sk/payload jen proto, že to očekává starý adapter. Monitoring využije existující identity a rozhraní; samostatné nové business list/detail API není cílem této dodávky.
- `case_id + document_id` je společná identita; `document_id` zachovat jako ingest `blob_id`. API i historie se vážou na tato ID, ne filename ani nový náhodný dokument při monitoringu.
- Upload metadata vlastní ingest, business výsledek vlastní document-analysis. Monitoring nepřepisuje originály, business hodnoty, `confidence`, label ani staré stavy svým odhadem.
- Před instrumentací určit skutečného producenta živých analýz a jeho publish bod; napojit nebo explicitně adaptovat zdrojový modul. Jeden processing owner, žádný druhý nezávislý OCR pipeline pro dashboard.
- Současné business entity se kvůli monitoringu znovu nevystavují v novém sjednoceném list/detail API. Case/document identitu ověřovat existujícím vlastníkem; audit-only historie se nesmí ztratit jen proto, že již není dostupný současný business objekt. Oprávnění musí být doložené i pro takový případ, ne odhadnuté z přítomnosti eventu.
- Legacy analýza bez událostí nemá doloženou historii: API přizná `not_instrumented`/unavailable podle existence identity a konfigurace. Nevymýšlet runy ani časy z `updated_at` a nevytvářet historický backfill.
- Pokud worker nadále potřebuje svůj pk/sk runtime store, je to samostatný owner-managed backend. Není totéž co audit ani existující analysis tabulka. Náprava kontraktu komponenty vůči současným business datům je oddělená změna, nikoli migrace schovaná do auditu; audit jejich formát ani publishing nemění. Podrobný soupis je v [rozdílech AWS a komponenty](../architecture/document-processing-aws-contract-differences.md).

**Acceptance:** mapování upload ↔ document ↔ job ↔ run ↔ publikovaný výsledek je doložené; existující tabulky/konzumenti zachováni; žádná domněnka source=deployed. Historický důkaz je v doprovodném AWS checkpointu, ne provozní dashboard data.

## Rozsah: pouze monitoring API, bez UI <!-- section:monitor-ui type:context -->
**Uživatelské upřesnění 19. 10. 2026 ve 21:10:** cílem je nasazené end-to-end API. Žádné obrazovky, frontend komponenty, klientský polling, screenshoty ani backoffice document management se neimplementují. Budoucí konzument si API načte samostatně. Dosavadní návrhy obrazovek a rozdělení podle vrstev jsou tímto nahrazené.

Do této dodávky nepatří sjednocené čtení současných upload/analysis entit, jejich filtry a legacy UI. Existující identitu, autorizaci a případné nezbytné safe read-through použít jako závislost konkrétního monitoring endpointu, nikoli jako samostatný produktový přírůstek. Pokud potřebné identity/oprávnění chybí, popsat konkrétní technickou překážku; nebudovat pod záminkou auditu nový business backend.

Zachováno: schválených 13 event typů, minimální historický run kontext a bezpečné reference známých vstupů/výstupů v událostech. **Upřesnění uživatele 19. 10. 2026 ve 21:26:** původní slice 11 (listování a načítání historických artefaktů) se z aktuální dodávky vyřazuje a odkládá na později. Žádné nové artifact/content endpointy, resolvery, presigned URL ani jejich content-authorizační implementace v tomto scope. Read-only monitoring nepřidává Retry/Cancel/Reprocess, editor, korekce, validace případu, globální dashboard ani nové inference.

## Společný slovník událostí a měření <!-- section:signals type:context -->
### Hranice fází
Pracovní slovník oblastí, nikoli garantované lineární pořadí: `file_received`, `source_validation`, `queued`, `page_transcription`, `extraction`, `signature_detection`, `result_publishing`, `terminal`. Přijetí uploadu eviduje business ingest; potvrzený scope auditu zahrnuje i událost `FileReceived`, nikoli kopii business uploadu. Skutečný časový sled určují zachycené události, včetně opakovaného ověření zdroje při pokusu.

V rámci stránky: `preview`, `native_text_assessment`, `native_transcription` nebo `vision_transcription`, `page_cache`. Volba `auto/visual` je konfigurace, native/vision skutečně provedená cesta. Nepřidávat uživateli umělé worker jobs pro každou dílčí funkci.

Klasifikace labelu/popisu a text/image embeddingy mají záznam capability/stage pouze pokud jejich producent existuje. Schválený krok `signature_detection` má doložený zdrojový hook; jeho události vznikají pouze při zapnutém detectoru, nikoli jako domyšlená historie. Návrhový validator-agent kontrakt a S3 Vectors nejsou důkazem, že tyto fáze dnes probíhají v tomto workeru. `not_instrumented`, `not_configured`, `skipped`, `pending` a „úspěch s nulovým počtem nálezů“ jsou různé věci.

### Kontrola naplnitelnosti — revize 0.3.2
Každý atribut musí mít konkrétního producenta: existující AWS business pole, existující SOURCE hodnota workeru, nový runtime event z HOOK na skutečné hranici nebo deterministická READ projekce. AWS/SOURCE business hodnoty se při čtení připojí z jejich vlastníka, nekopírují se do auditního deníku. Historický runtime kontext je výjimka pouze v minimálním rozsahu nutném k doložení konkrétního běhu. [Průvodce](../../be-document-processing/PROCESSING-MONITOR-API.md#revize-podle-skutečných-producentů-030) uvádí mapu všech entit na konkrétní zdrojové body a oddělení čtecích business pohledů od první zapisované entity Event. SOURCE není důkaz nasazení. Nové auditní ID/sequence/revision a časování vytváří auditní listener, ale business chování nemění; nezachycenou událost nesmí zpětně vymyslet.

Z kontraktu odstraněny původní run/attempt cache, tokeny, cena a queue wait; pravidelný heartbeat ani hash kódu/promptu nejsou součást scope. Cache hit a důvod fallbacku zůstávají jen z konkrétních větví. Preview/result/cache artifact nemá historickou neměnnost bez potvrzené verze/provenance. Detailní soupis v průvodci má přednost před obecnými ilustracemi.

### Co číst dnes vs co přidat
- **Přijetí a identita — dnes:** case/document, typ/velikost souboru, received_at, hash/S3 reference; v source workeru page_count a neměnná source_version. **Doplnit:** `RunQueued` s identitami a minimální historickou referencí na použitou verzi vstupu; nikoli kopii ingest objektu nebo jeho metadata.
- **Fronta a worker — část dnes:** job.status, attempts, owner a lease, created_at. **Doplnit:** auditní claim/start/finish/requeue časy na existujících hranicích a známý retry error code. Periodický heartbeat a `queue_wait_ms` nejsou součást MVP; chybí per-attempt enqueue evidence.
- **Stránky — dnes:** cache Page s method/model/text/blocks/tables/visual_marks/warnings/error; fallback reason je ve warnings. **Doplnit:** průběžnou dostupnost přes API, started/finished/duration a cache_hit z úspěšné cache read/validate větve. Cache neobsahuje původní run/attempt: source_attempt reference se nevrací; retry count patří k pokusu, ne k neexistující stránkové historii. Žádné další LLM volání kvůli monitoringu.
- **Extrakce — dnes:** typ dokumentu, fields, normalizace, citace, model, warnings, evidence validation. **Doplnit:** runtime start/end extrakce a měřené trvání. Hodnoty, citace, stav i počty polí číst z existujícího autorizovaného výsledku; neukládat je do auditu. Nedělit počtem všech možných fields jako údajnou úplností.
- **Výsledek a audit — dnes:** result JSON s run/attempt/config/elapsed/completed_at a oddělené korekce; živá analysis má zploštěný snapshot. **Doplnit:** `ResultPublished` s referencí na skutečný výstup/verzi a outcome; historii běhů/pokusů tvoří runtime události. Žádná kopie výsledku nebo nové auditní analysis záznamy.
- **Spolehlivost — doplnit:** pozorované first/last error, kód, fáze/stránka, známé retryable a uskutečněné requeue. Neznámý pád/ztrátu lease nebo plánovaný čas retry nelze hlásit jako zachycenou událost; chybějící konec zůstane unknown. Freshness je stáří poslední zachycené hranice, ne důkaz živosti. SQS delivery count je jiná metrika než počet worker pokusů; globální DLQ/queue age jsou agregované AWS metriky, ne stav jednotlivého dokumentu.
- **Latence — dnes:** výsledkové elapsed_seconds pokusu a konfigurace. **Doplnit hookem:** stage duration a `client_call_duration_ms` kolem existujícího `BedrockClient.complete`; to zahrnuje lokální práci/SDK retries, nikoli čistou provider latency. **Vyřazeno:** tokeny a cena; klient vrací jen text a usage nepropaguje. Bez instrumentovaného měření chybí hodnota/null, nikoli nula.
- **Kvalita:** VLM OCR bbox/confidence mohou být null, to je platné. Živé `confidence` je dle kontraktu klasifikační skóre, ne kalibrovaná OCR přesnost. CER/WER jen proti anotovaným evaluacím, ne „přesnost živého dokumentu“ bez reference. Podpis/razítko ani semantic consistency nejsou ověření pravosti.

ProcessingStatus zůstává `awaiting_upload|queued|processing|completed|partial|failed`. `stale` je samostatné pozorování freshness, nikoli automatická změna na failed. Stav kroku: `pending|running|succeeded|failed|skipped`; absence coverage/instrumentace je samostatný atribut.

**Acceptance:** slovník metrik uvádí jednotky, zdroj a null semantics; chybějící signál se nevydává za nulu nebo úspěch.

## Společný datový kontrakt a ownership <!-- section:data-model type:context -->
### Co zapisujeme a co pouze čteme
1. **`wonderfulkb-uw-documents`:** jediný vlastník originálu a ingest metadata. Název, MIME, velikost, upload čas, uploadér a současný hash/odkaz se čtou odsud. Audit nekopíruje Upload ani Document.
2. **`wonderfulkb-uw-document-analysis`:** jediný vlastník současného business výsledku; zachovat klíče, pole, význam i publishing. Název/popisek, label, confidence, business status, počet stran, hodnoty a textové odkazy čteme odsud nebo z existujícího výsledku. Audit sem nepřidává žádná pole a nevytváří druhý Analysis snapshot.
3. **Nová úzká tabulka `wonderfulkb-uw-document-processing-audit`:** append-only runtime **Event**. Běh/pokus/krok/stránkový průběh jsou projekce těchto událostí. Nezapisujeme zvlášť business entity a pak ještě událost o jejich kopii. Runtime job/lease store je nadále výhradním execution ownerem, není auditní autoritou.
4. **S3:** business obsahy/cache/preview/výsledky mají dosavadní cesty a lifecycle. Události obsahují pouze bezpečné interní reference na skutečně potvrzený objekt/verzi. Žádný nový auditní manifest kopírující dokument, job, konfiguraci nebo výsledek. Velké obsahy se neukládají do auditu; generování presigned URL a nové čtení obsahu jsou mimo aktuální scope.

### Jediná primární zapisovaná entita: Event
**Obálka sjednocená schválením 19. 10. 20:17:** `schema_version`, `event_id`, `case_id`, `document_id`, `sequence`, `type`, `occurred_at`. Události tvoří dokumentovou časovou osu; `FileReceived` nemá `run_id`, pro ostatní schválené události zpracování je `run_id` povinné. Scope podle typu: `attempt_no`, `stage`, `page_number`, `correlation_id`. Jediný ukládaný event timestamp je `occurred_at`, zachycený producentem na skutečné hranici akce, nikoli při pozdějším zápisu listenerem. **Čas uložení/doručení auditu neukládáme ani nezobrazujeme.** To se netýká monotónního měření business kroků ani času pozorování API odpovědi.

`sequence` je jen technické stabilní pořadí pro čtení, ne další časový údaj ani důkaz kauzality či úplnosti. Dokumentová časová osa používá čas vzniku, při shodě deterministický tie-break; pořadí pozdních zápisů nesmí přepsat význam událostí. Samotné chybějící číslo či opačné pořadí příchodu není důkaz ztráty nebo business chyby. V MVP refresh začíná novou stránkovací relaci od začátku; incremental late-event catch-up je odložený. Nepřidávat kvůli němu čas zápisu do Event ani recovery mechanismus.

Payload má jen fakta příslušného runtime přechodu: outcome, změřené trvání, skutečně použitou cestu/model, úspěšné použití cache, známý fallback/warning code, bezpečný error a reference vytvořených/použitých artefaktů. Žádný název souboru, titul/popisek, MIME, velikost, uploadér, label/confidence, vytěžené hodnoty, přepis či raw provider request/response. Text chyby je mapovaný bezpečný popis kódu, nikoli libovolná výjimka s dokumentovým obsahem.

**Historický kontext běhu — parametry schválené uživatelem 19. 10. 2026 ve 20:30:** `RunQueued` může jednou zachytit `job_id`, `config_hash`, deklarované pipeline/prompt verze, režim, provider/API/region a konfigurované OCR/extraction modely, pokud nejsou dostupné přes neměnnou referenci. Reference zdroje zahrne skutečnou verzi nebo známý hash pouze pokud samotné ID dokumentu nedokládá použitý vstup. Preferovat existující neměnnou referenci; nekopírovat celý job/config/source objekt. Jde o důkaz „s čím tento běh skutečně začal“, ne druhou autoritu pro aktuální data. Další události tento kontext neopakují. Pokud ref chybí nebo zanikne, historický obsah zůstane unavailable, nepodstrčí se aktuální objekt.

### Persistence a access patterns
Základ deníku je dokumentový, nikoli povinně runový: návrhové `pk = CASE#<case_id>#DOC#<document_id>`; MVP sort/cursor dokládá bounded čtení dokumentu; run filtr a incremental late-event refresh jsou pozdější rozšíření. `run_id` je atribut pouze událostí běhu, ne požadavek na FileReceived. Immutable put s idempotencí podle event identity; repeat doručení uloženou událost nemění. Technická sequence není čas zápisu ani kauzální záruka. Stabilní sort nenabízí snapshot ani incremental late-event refresh; MVP umožní začít nové stránkování od začátku. Žádný zapisovaný event timestamp pro uložení/doručení a žádná business blokace.

Pozdější rozšíření pro řazení běhů a case audit-only identity může řešit sparse indexy přímo nad `RunQueued` (document/time/run a case/document/run), nikoli nové dokumentové kopie. Případný run s chybějícím úvodním eventem musí být dohledatelný jako partial: přímý run lookup a index membership z ostatních událostí, nebo malý odvozený runtime index bez business polí. Konkrétní bounded návrh ověřit před implementací; sparse index pouze na chybějícím RunQueued by takový běh skryl.

API `Run`, `Attempt`, `Step`, `Page`, `AuditSnapshot` jsou **čtecí DTO**, ne automatický seznam DynamoDB itemů. MVP nevyžaduje současně CURRENT + RUN/META + ATTEMPT/META + STEP + kopii Event. Výchozí je event deník; pokud bounded polling/listing vyžaduje materializaci, povolit jen minimální odvoditelný runtime index/projekci s doloženým dotazem a cenou. Obsahuje ID/event cursor a stav z událostí, žádné business atributy, celé config objekty nebo výsledky. Takovou projekci lze obnovit z dochovaných událostí bez business replay/inference; mezery tím nezmizí. Čtení nesmí při každém pollu bez limitu přehrávat celou historii.

Monitoring API čte události a odvoditelné runtime pohledy pro existující case/document identitu. Nový union business upload + analysis list/detail není součástí této dodávky. Stránkové DTO obsahuje pouze runtime průběh; obsah historických stránek/artefaktů se v aktuální dodávce nepřipojuje. Reference v události není download endpoint ani příslib dostupnosti; současný business obsah se nesmí vydávat za obsah tehdejšího běhu. Žádný Scan celé tabulky na refresh, žádný horký globální status index pro MVP.

**Acceptance:** auditní zápisy jsou pouze allowlistované best-effort runtime události a nezbytné odvoditelné runtime indexy. Testy ověří absenci business atributů/obsahů, idempotenci, bounded query, čitelnost mezer, historické reference a oddělení aktuálního business pohledu od časové osy. Žádná změna business schématu nebo kopírování business entit.

## Společné architektonické a fail-open hranice <!-- section:instrumentation type:context -->
### Izolace implementace
Umístění: **`be-document-processing/src/document_processing/audit/`**, interní package stejné služby, ne nový kořenový modul nebo samostatná knihovna/service. Audit má vlastní event kontrakt, listenery, storage adapter a query/projection logiku. Business pipeline nesmí importovat boto3 pro audit, sestavovat DynamoDB itemy či S3 klíče auditu, nastavovat jeho retenci ani obsahovat jeho retry/catch bloky.

Návrhové rozdělení (soubory jsou návrh, ne existující implementace):
- `audit_events.py` — typované immutable události a malý `AuditListener`/`AuditSink` protokol; explicitní correlation/run/attempt/page context.
- `audit_listener.py` — konkrétní listener, bezpečná serializace/redakce, idempotence, fencing auditní projekce, skládání read modelu a izolace chyb.
- `audit_storage.py` — append-only DynamoDB deník a jen odůvodněné odvoditelné runtime indexy; žádný zápis do business tabulek ani nový business manifest.
- `audit_queries.py` — stránkované auditní čtení a DTO; stávající HTTP router jen deleguje, nezavádí novou aplikaci.
- `audit_instrumentation.py` — úzké wrappery/dekorátory/context managers pro měření a start/finish/failure události, pokud skutečně zjednoduší kód; `NoOpAudit` pro vypnutí a testy.
- `__init__.py` — malé stabilní veřejné rozhraní a factory pro zapojení v existujícím composition rootu. Nevytvářet plugin registry ani obecný event bus.

Preferovat **jeden injektovaný listener** s explicitními sémantickými událostmi (`RunQueued`, `AttemptStarted`, `StepStarted`, `StepFinished`, `PageCacheReused`, `PageCompleted`, `PageFailed`, `ResultPublished`, `RetryEnqueued`, `AttemptFinished`, `RunFinished`); přesné názvy/kontrakt stanoví implementační návrh. V hlavním toku jen vytvoření události s hodnotami, které už zná, a předání přes malé rozhraní. Událost po business zápisu říká, že zápis skutečně uspěl, ne jen že byl zamýšlen. Dekorátor sám nestačí pro cache-hit, partial či ztrátu lease; tyto sémantické body musí být explicitní. Žádné monkey-patching, globální mutable context nebo rozesílání kopie všech dokumentových hodnot do auditu.

Zapojení závislostí: `composition root → business service/worker + audit listener`; `business → malý event protokol`; `audit → vlastní persistence`. Audit nevolá zpět business kroky ani si nečte jeho interní mutable objekty. Čtecí server-side projekce může spojit business a audit data, ale nevytváří tím novou business autoritu.

### Provozní pravidla
- Instrumentovat skutečný ingest commit pro FileReceived a doložené enqueue/claim hranice (source `complete_upload` není automaticky živý ingest), stránkový cache hit/OCR, extrakce, publish a retry. Veškeré chování navíc držet v package výše, nikoli rozprostřené po `pipeline.py`, `service.py`, `bedrock.py`. Nevytvářet druhý worker, globální tracing platformu nebo přepis algoritmu jen pro monitoring.
- Runtime job/lease zůstává jedinou autoritou pro exekuci. Telemetry je projekce runtime událostí; business výsledky se čtou od jejich vlastníka. Audit nesmí sám spouštět retry ani rozhodovat o ukončení práce.
- Event idempotency key odvozovat z run/attempt/stage/page/transition; retry doručení nesmí přičíst completed stránky dvakrát. Existující runtime owner/lease fencing zůstává jedinou ochranou exekuce. Případná odvoditelná čtecí projekce má vlastní monotónní revision a nesmí být přepsána opožděnou událostí; není novou autoritou jobu ani povinným CURRENT; cache hit eviduje úspěšné použití konkrétního cache artefaktu, netvrdí novou OCR inferenci ani původní run/attempt, který cache dnes neukládá.
- **Žádná společná audit+business transakce jako nová podmínka business úspěchu.** Existující publishing, owner/lease ochrany i transakce se auditem nemění. Listener dostane `ResultPublished` až po úspěšném existujícím publish bodu a ukládá samostatný auditní záznam. Je-li producent externí, potřebujeme jeho explicitní událost/adaptaci, ne odhad stavu z auditní tabulky.
- Audit referencuje pouze již potvrzené business artefakty a zachovává jejich originální cesty/verze. Auditní zápis obsahuje malou referenci události, ne nový manifest kopírující tyto business objekty; retence se týká jen auditního deníku/indexů. Nemění tím lifecycle business souborů.

Platí pro `FileReceived` i všechny události zpracování, nikoli pouze upload. Současné business commit/publish hranice (`be-intake/app/main.py:220–230`, `be-document-processing/src/document_processing/pipeline.py:125–139`) se tím nemění.
- **Žádné řešení spolehlivého doručení v tomto scope:** žádný durable outbox, fronta nedoručených auditů, samostatný retry/recovery/replay mechanismus ani povinné pozdější doplnění ztracených událostí. Auditní I/O musí mít krátký konečný timeout bez auditní retry smyčky; nepřidávat čekání na obnovu sinku ani nekonečné SDK retries. Případný jednoduchý bezpečný log je pouze diagnostika, nikoli náhradní deník nebo závazek obnovy; jeho selhání také neovlivní business tok.

MVP negarantuje úplnost ani detekci každé ztráty; API nesmí z chybějící události odvodit neúspěch či neprovedení business akce, chybějící konec zůstává unknown a rozpoznané mezery partial. Pozdější event nevymýšlí chybějící historii. Návrh trvalého podkladu pro pozdější doručení byl výslovně odmítnut; není to otevřený implementační požadavek.

**E2E a dotažení celé sekce:** na novém syntetickém test fixture potvrdit skutečnou cache větev a následné HTTP evidence bez nového model call. Chybějící/poškozená cache neprodukuje reuse. Pokud nelze scénář bezpečně vyvolat existujícím test vstupem bez replay/business změny, ohlásit přesný runtime blocker, nebudovat nový reprocess endpoint. Read rozšíření zahrnuje skutečný AWS test deployment a live HTTP ověření/doladění. Event/store a read části samy nedokládají skutečný worker hook/build ani úplný AWS worker→HTTP smoke; ty zůstávají navazující dodávkou s doloženým producerem a execution kontextem.

## Slice 7 — Skutečná extrakce → její outcome přes API <!-- section:slice-extraction -->
**Použitelný výsledek:** v steps/events lze číst provedení extrakce a pozorovaný úspěch/chybu bez hodnot dokumentu.

**Celá cesta:** existující `pipeline.py:104–111` → stejné Step typy se stage extraction → deník a HTTP mapping. Spustit pouze s neprázdným completed seznamem. Hodnoty/citace nepatří do auditu; pole chybějící v platném výsledku není automaticky pád kroku.

**Malé samostatné dodávky, stejný MVP vzor:** (a) rozšíření existujících StepStarted/StepFinished/StepFailed event/store kontraktů o stage=extraction, (b) rozšíření existujícího steps a document/run events GET, bez nového endpointu. Povinný předaný run/attempt, bez page scope. Trvání pouze skutečně monotónně změřené finite nezáporné duration_ms, chyba jen bezpečný error_code. Nevyžadovat v deníku úvodní eventy jako podmínku přijetí doloženého výsledku; chybějící konec unknown. Žádné fields, quotes/evidence, raw output/config nebo counts z dokumentového obsahu. Prázdná platná extrakce není automaticky failure a lokální extractor není důkaz cloud call.

**Read MVP:** extraction Step observations používají stejný bounded evaluated document Query/partial okno jako source_validation, cursor vázaný na run/operation/attempt, empty continuation legitimní. Bez celohistorického párování, nového indexu/projekce či tvrzení o posledním/úplném stavu. Pages view non-page extrakci nezobrazuje. Case auth/no-store/read503 a předchozí GET zůstávají.

**E2E a dotažení celé sekce:** doložit skutečný hook a HTTP čtení na bezpečné test cestě; success/error s fake extractorem jsou označené hermetické důkazy, ne live provider success. Žádné completed stránky = žádné předstírané spuštění. Bez změn extractor pravidel nebo provider-call počtu. Read rozšíření zahrnuje skutečný AWS test deployment a live HTTP ověření/doladění. Event/store a read části samy nedokládají canonical worker hook/build ani celou worker→HTTP cestu; ty zůstávají navazující dodávkou, nikoli výsledkem hermetické fixture.

## Slice 8 — Zapnutý signature detector → pravdivý outcome přes API <!-- section:slice-signatures -->
**Použitelný výsledek:** steps/events odliší skutečné dokončení a selhání zapnutého detectoru; vypnutý nic nefinguje.

**Celá cesta:** `pipeline.py:114–115`, skutečný status sekce ze `signatures.py:153–163` → Step události signature_detection → deník + HTTP. Návrat bez výjimky nemusí být úspěch; completed s nulou nálezů úspěchem být může. Bez podpisových hodnot/citací a bez změny OCR processing statusu.

**Malé samostatné dodávky:** signature_detection Step event/store kontrakt a rozšíření již existujících steps/document/run events GET. Stejný run/attempt scope bez page, skutečně měřené duration_ms a bezpečný error_code, žádné podpisové hodnoty/counts/config. Čtení používá stejné bounded evaluated partial observation okno a operation/attempt-bound cursor, empty continuation legitimní; bez nového endpointu/projekce. Disabled ani chybějící konec nevyrábějí success/skipped/failed. Returned-failed je failure i bez raised exception; completed-empty je úspěch.

**E2E a dotažení:** ověřit skutečné zapojení detectoru a endpointu, hermeticky všechny returned/raised failure a disabled větve; nedoložené živé model volání se nevydává za provedené. Chybějící historická signature konfigurace se nedoplňuje z dnešního prostředí. Kontrakt/read části doplňuje společná skutečná worker instrumentation a worker→HTTP integrační dodávka; nepodporovaná canonical stage zůstává explicitní blocker, ne nový business detector kvůli auditu.

## Slice 9 — Dokončená publikace → publikovaný výsledek v API <!-- section:slice-result-published -->
**Použitelný výsledek:** events/steps a run detail dokládají skutečně publikovaný outcome a bezpečnou referenci výsledku; obsahové API je mimo aktuální scope.

**Celá cesta:** celý publish `pipeline.py:125–130` → Step result_publishing + ResultPublished → deník a HTTP. Teprve validace/S3/owned job update/document update dohromady dovolují pozorovaný publish success. Partial výsledek nemusí znamenat konec runu. Reference nedokazuje historickou neměnnost sama o sobě.

**Malé samostatné dodávky:** result_publishing Step a ResultPublished event/store; rozšíření existujících steps/document/run events GET. ResultPublished nese skutečný result_status=completed/partial/failed a jen doložené opaque artifact reference, nikoli run terminal nebo kopii výsledku. Step a fakt publikace mají odlišné event identity. Stejná partial evaluated-window read politika, žádný nový content endpoint/projekce; run-detail summary dodává lifecycle část.

**E2E a dotažení:** syntetický výsledek publikovaný existujícím test workerem je dohledatelný přes HTTP. Každý neúspěšný publish bod, S3-only success a stale owner mají negativní test; audit nesmí měnit pořadí writes, rollback, retry ani publikovat za fenced worker. Žádná kopie business výsledku do auditu. Skutečné publish hooks a full-path proof dodává společná worker instrumentation/integration, ne store fixture; pokud canonical worker nemá totéž owned/fencing rozhraní, nepřidávat nové execution chování pod záminkou auditu.

## Slice 10 — Retry a skutečné konce → lifecycle a audit snapshot přes API <!-- section:slice-retry-terminal -->
**Použitelný výsledek:** events, runs/attempts a `GET .../{document_id}/audit` rozlišují ukončený pokus, nové skutečné předání frontě a skutečně terminální run.

**Celá cesta:** úspěšné requeue `pipeline.py:131–146`, potvrzené konce a max-attempt větev → RetryEnqueued, AttemptFinished, RunFinished → bounded odvozený lifecycle snapshot a HTTP. Samotné queued není requeue; partial publish není vždy konec; konflikt/ztráta lease/nezachycený pád nejsou automatický terminal.

**Malé samostatné dodávky:** RetryEnqueued/AttemptFinished/RunFinished event/store kontrakt; čisté bounded in-memory lifecycle odvození nad jediným evaluated event oknem; case-scoped runs/run-detail/document audit GET. RetryEnqueued nese odcházející skutečný attempt, ne příslib nového. RunFinished bez attempt je legitimní při max-attempt větvi bez nového claimu. Žádné nové business retry nebo auditní execution identity.

**Read MVP:** runs/snapshot jsou summaries pozorování v omezeném okně, nikoli úplný execution registr, last/latest pravda nebo stored projekce. Povinné coverage=partial, observed_at/next_token, jeden bounded document Query a operation-bound last evaluated cursor; empty continuation legitimní. Chybějící run observations v aktuálním okně samy nejsou autoritativní run404; document/case scope zůstává trusted zdrojem. Konfliktní terminal/late observations bez prokazatelného execution pořadí znamenají unknown/ambiguous, ne heuristicky poslední audit sequence/occurred_at. AttemptStarted list zůstává seznam pozorovaných zahájení, nedoplňují se chybějící attempts. Availability not_configured/not_instrumented pouze s konkrétní konfigurací/capability důkazem, absence eventů sama unknown; nutný read failure503. Žádný scan-until-filled/replay celé historie/totals/procenta či snapshot completeness.

**E2E a dotažení:** bounded syntetická retry cesta a následné HTTP čtení stejného runu s různými pokusy, terminální completed/partial/failed podle potvrzeného execution stavu. Queue failure, max attempts bez nového claimu, reorder, mezery/late event a stale-owner fencing. Doložit rozdíl not_configured/not_instrumented/unknown/read failure; žádný nový business retry nebo outbox. Společné worker hooks a skutečná worker→audit→HTTP hermetická integrační cesta jsou samostatné dodávky níže; Každá read dodávka obsahuje vlastní skutečné nasazení a live HTTP důkaz; plný producer→HTTP důkaz je navíc součást společné integrace s runtime operacemi dle delivery pravidla.

### Společné dotažení producerů a worker→HTTP, bez rozšíření business scope
Po kontrakt/read částech jsou potřebné tři konkrétní dodávky: (1) autoritativní runtime context a skutečné queue/claim producer volání, navázané na slice-attempt-started; (2) skutečné worker audit hooks pro podporované stage, navázané na slice-retry-terminal; (3) skutečný hermetický entrypoint→store→HTTP integrační test, build inclusion a hostitelský deployment/smoke runbook, navázané na slice-retry-terminal. Nejsou samostatnou obecnou discovery ani povolením zavést druhý worker/outbox.

Chybějící run/attempt allocator a canonical source/build nebo trusted case auth jsou skutečné technické vstupy. Nelze je nahradit UUID z auditu, SQS receive-count attemptem, spekulativní audit-owned runtime tabulkou nebo změnou business claim/fencing/retry chování. Úzký oddělený execution-owned stav je nyní výslovně schválen dle slice 3; dřívější široký runtime-table/outbox návrh tím schválen není. Integrátor použije skutečně dodaný execution interface se schválenými sémantikami; no-op adapter nebo starý DocumentWorker není živá integrace. Podobně stage nepřítomná ve skutečném produceru se nesmí přidat jako nová business funkce pouze kvůli auditu.

Event-only dodávky zůstávají v source/test scope. Každá read dodávka a závěrečná integrační dodávka zahrnují skutečné instalace/test deployment/live HTTP a doladění agentem podle delivery pravidla, s host operator pomocí jen při reálném omezení runtime. Neprovedený smoke runbook ani byte shoda dvou modulů nejsou nasazená provenance/success. Přesné partial-window read kontrakty se synchronizují do jediného YAML při příslušných read dodávkách.
