2. **Collection schema lacks the required operation-specific allowlisted item contracts.** YAML `:108-139` defines one generic `ObservationCollection` and `ObservationItem` with generic `details` and an undifferentiated union of event fields. Focused test `tests/test_monitor_openapi_observation_contract.py:64-83` explicitly requires `details` (`:73`), but YAML has no such property; after syntax repair it would fail. More substantively, a generic `ObservationItem` permits arbitrary cross-type combinations (including FileReceived with run scope, RunFinished attempt fields, page-only fields on non-page events) and cannot express the brief-required per-event allowlists / required fields and distinctions. This misses the task's “precise types/schema allowlist” requirement and defeats the intended safeguards. Briefs 03/07/09/11/13/15/17/19/21/22 establish the type-specific scope and field semantics.
3. **`additionalProperties: false` is only applied to each item, but not backed by type discrimination.** Although this helps prevent unknown keys, the shared `properties` union in `:121-139` still accepts wrong known keys for any event. For example `FileReceived` can carry `run_id`, `attempt_no`, `page_number`, model/method; run terminal events can carry page-specific attributes. Explicit per-type schema variants (e.g. `oneOf` with discriminator/enum and strict properties) or equivalent schema constraints are needed.
4. **Lifecycle contract response is not distinguished from event items.** Paths `:62-82` correctly identify the three Brief 24 operations, but all point to the same `Observation` response/schema (`:33-82`, components `:95-115`) and one `ObservationItem` event union. Brief 24 requires bounded run summaries/detail/audit with lifecycle unknown/ambiguous/partial, evidence, publication result separated from run terminal status; current schema has no typed lifecycle summary/detail/audit shape or guaranteed distinction (only optional `lifecycle`/`result_status`). Also no `attempt_status`/`run_status` fields are specified. Bounded paths are in scope; omission of their actual DTO semantics is not.
5. **Auth/security statement has a tension needing precise treatment.** Info `:7-13` appropriately says trusted identity-to-case interface is unavailable and shared key is insufficient. But global OpenAPI `security: ApiKeyAuth` at `:24-25` makes the API key appear to be the sole operative security scheme unless its role is expressly limited as service authentication in each applicable security contract. It does describe that at `:85`, so not independently blocking, but should ensure this is not read as case authorization. Response `Observation` (`:96-102`) describes error statuses in text but formally only documents the successful JSON body; `Failure` (`:103-106`) is defined but unused. Since errors must be `private,no-store`, the success response header alone does not contractually define explicit 400/403/404/503 response headers/bodies for operations.
