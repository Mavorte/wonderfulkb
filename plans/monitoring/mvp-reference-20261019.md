# Monitoring MVP: scope a ověřené reference

## Revize podle požadavku 19. 10. 2026
Jednoduchá implementace, krátké cílené ověření; výjimečné scénáře ladit později. Tento MVP rozsah nahrazuje rozsáhlejší acceptance prvních dvou slices ve starších zadáních. Bez změny povinných pipeline gates, zabezpečení či business dat.

Všechny monitorovací GET budou jeden FastAPI router ve stávajícím `be-intake` na App Runneru pod `/v1/cases/{case_id}/processing/documents`. Žádná další aplikace, API Gateway, Lambda nebo deploy jednotka. To je jeden monitoring API povrch na stejné adrese jako upload, **nikoli** sloučení všech ostatních API. Case & Client má nadále samostatnou API Gateway/Lambda. Auditní implementace zůstává interní Python package v `be-document-processing`; intake image jej musí skutečně nainstalovat. Nenakopírovat jeho logiku do intake.

### Minimum společné prvním taskům
- První FileReceived, poté samostatně RunQueued a AttemptStarted dle rozšíření níže. Malá auditní DynamoDB tabulka, idempotentní conditional put, fail-open s konečným SDK timeoutem. Žádné business kopie, obsah dokumentů či credentials.
- Document-partition Query, limit 1–100 a scope-bound continuation. MVP nemá incremental polling, snapshot/revision/fencing, watermark ani garanci zachycení libovolně pozdních událostí během rozběhnutého stránkování. Refresh znamená začít nové stránkování od začátku; netvrdit kompletní historii. `occurred_at` zůstává jediný uložený timestamp; interní stabilní identita/sequence není čas uložení. Žádný globální Scan. Žádná automatická TTL v této dodávce.
- API: JSON, no-store, 404 pro cizí/neexistující document scope, chyba nutného zdroje 503. Zachovat autentizaci; samotný sdílený klíč není uživatelská case autorizace. Chybějící důvěryhodnou autorizační hranici neřešit fake claims ani novým auth frameworkem: pojmenovat konkrétní blocker. MVP zjednodušení není souhlas k úniku mezi případy.
- Cíleně happy path + duplicate/fail-open pro zápis; happy path + scope/auth + read-error pro API. Ne rozsáhlá matice chaosu, TTL, replay, cache, inference, lease a všech dalších eventů. Registrované gates se nemění.
- Každý read přírůstek zahrnuje skutečné AWS test nasazení agentem přes existující podporovaný postup, přímý HTTP důkaz a doladění; host pomáhá jen s runtime-inaccessible operator krokem v témže zadání. Samostatný první smoke navíc ověřuje bezpečný syntetický upload → HTTP GET; zaznamenat stav/ID/revizi bez obsahů. Žádný replay ani neautorizovaná inference. Nevyrábět vlastní deployment framework nebo plošné cloud testy.

## Rozšíření sekcí 2 a 3 — zadání 23:02
Název **Processing Monitor API**, jediný router `be-intake/app/processing_monitor_routes.py` ve stávajícím wonderfulkb-ingest Python/FastAPI App Runneru, stejný host jako upload (aktuálně https://vt9mavpjky.eu-central-1.awsapprunner.com; ne hardcoded konfigurace). První GET `/v1/cases/{case_id}/processing/documents/{document_id}/events`, limit a next_token, JSON items/next_token/observed_at. Tento deployment kontrakt platí i pro všechny navazující monitor GET.

RunQueued MVP se dělí na (a) společné krátké read-only doložení canonical zdroje a execution identity pro enqueue/claim, (b) event/store kontrakt s povinným reálným run_id, (c) jediný GET `/v1/cases/{case_id}/processing/documents/{document_id}/runs/{run_id}/events`. Run list/detail, široký config snapshot a run indexy odloženy.

AttemptStarted MVP přidává (a) event/store kontrakt s reálným run_id a attempt_no, (b) jediný GET `/v1/cases/{case_id}/processing/documents/{document_id}/runs/{run_id}/attempts` jako pozorované AttemptStarted observations (event_id, attempt_no, occurred_at), nikoli kompletní execution projekci. Oba GET sdílejí první API auth a no-store/error politiku.

Oba nové GET používají jeden bounded document Query evaluated-window. Filtr nepřináší scan-until-filled smyčku: i empty items mohou mít next_token, který pokračuje od posledního vyhodnoceného eventu a je vázaný i na operaci/run. Žádné Scan, tvrzení o kompletnosti, umělé totals/status nebo nový index.

**Doložená mezera, nikoli ready producer implementace:** `live-trigger-evidence-20261019.md` potvrzuje z aktuálního ZIP/image source absenci run_id v queue a attempt counteru v claimu; canonical source owner není v checkout/main doložen. Proto nyní nezadávat executable hook ani live RunQueued/AttemptStarted smoke s vymyšleným workerem/identitou. Specifikovat a registrovat lze uvedené samostatné kontrakt/read části a read-only prerequisite; jejich hermetické testy nejsou celý vertikální slice. Skutečný hook/build + bounded AWS producer→HTTP smoke pro každou z obou sekcí zůstávají výslovně nedodané další zadání po vyřešení tohoto vstupu. Nutná změna business execution identity je oddělené rozhodnutí, ne oprávnění k auditnímu workaroundu.
