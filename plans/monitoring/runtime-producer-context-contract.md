## Finding

No eligible source integration can be implemented from the checked-in execution interface. The evidence in `plans/monitoring/live-trigger-evidence-20261019.md` identifies the trigger candidate at `be-validator-agent/trigger/common.py` and `worker_handler.py` by byte equivalence to the observed deployed modules, but does not establish full image/build provenance or a canonical complete build caller. The exact observed deployed worker image digest is `sha256:8603c8389fd1aab9a073cc996ed34d346fcc877270b5ba190d265826d4a45591`; the observed shared module hashes are recorded in that evidence. The candidate source ref is not authorization to replace or fetch source.

The checked-in enqueue caller in `be-validator-agent/trigger/common.py` writes the business row as `queued`, then `Context.send` calls SQS `send_message` and discards its response. `enqueue_document` returns `queued` only after send returns, but has no stable event/run identity to associate with that response. A crash after SQS accepted the message but before returning/recording success is ambiguous; retries can send duplicates. It cannot distinguish confirmed enqueue from ambiguous delivery for audit semantics.

The checked-in claim is a conditional update from `queued` or expired `processing` to `processing` using the 930-second lease. It writes no attempt ordinal, run ID, or claim owner token. The worker calls `run_document(case_id, document_id, options=options())` only after a claimed result; `Options` is warm-container cached and contains no per-execution identity. `ApproximateReceiveCount` is only logged on the error path. Therefore there is no authoritative claim+attempt result and no immutable per-execution context to forward. Duplicate messages currently produce harmless failed claims; adding a counter or identity would change execution/claim semantics absent an execution-owner decision.

## Smallest required execution-owner contract

Before producer integration, the canonical execution owner/build caller must approve and implement an interface with these semantics:

1. **Enqueue event identity and result:** create/stabilize a run identity for one logical enqueue event and return a typed outcome that distinguishes confirmed SQS acceptance from definite rejection and ambiguous send (including process crash after acceptance). Retries of the same logical event must retain the same identity. Confirmed acceptance must be associated with durable logical enqueue state if required to resolve ambiguity; the execution owner must decide how this occurs without changing current retry/DLQ behavior or adding an unapproved outbox.
2. **Claim+attempt atomicity:** a single atomic authoritative operation returns either unclaimed (no attempt increment) or claimed with stable `run_id` and monotonically assigned `attempt_no`. The increment and claim must be committed together under concurrent/duplicate deliveries. The owner must explicitly decide expired-lease retry semantics and how a crashed worker's attempt remains distinguishable, without silently introducing fencing/supersession.
3. **Explicit context forwarding:** worker passes an immutable execution context from the successful claim as a direct argument through the canonical `run_document` caller into `Options`/downstream execution; no module global, cached warm-container identity, environment identity, SQS receive count, or mutable business object copy.
4. **Audit boundary:** one injected listener port receives only the minimum values at confirmed enqueue and successful claim boundaries. RunQueued follows only confirmed enqueue; AttemptStarted follows only the atomic successful claim+attempt result. Event construction, validation, stable event ID derivation, serialization, audit I/O, and fail-open exception isolation belong to the approved central audit implementation, not the business runtime caller.

## Decision

Technical blocker confirmed by the implementation follow-up (2026-10-20): the owned `be-validator-agent/trigger/build.sh` stages `common.py`, `worker_handler.py` and pipeline modules into build artifacts but does not establish provenance for a canonical deployed image/build. In the checked-in caller, `Context.send` still discards the SQS response; `enqueue_document` has no logical run identity or confirmed/ambiguous outcome. `claim_document` remains a conditional queued/expired-processing state update that returns a status string, with no atomic attempt ordinal or stable run identity. `process_document` calls `run_document(case_id, document_id, options=options())`; warm-cached `Options` carries no per-execution immutable context. No compatible approved interface was found in the owned trigger source, and the applicable trigger suite did not complete because collection fails in `tests/test_backfill.py` (`ModuleNotFoundError: No module named 'backfill'` from the repository-root invocation); this collection failure is not evidence for or against an identity interface.

Do not implement speculative producers or context propagation, and do not report source integration as complete. The execution owner must first establish canonical build ownership and approve the smallest interface in the preceding section, including durable/stable enqueue identity and confirmed/definite-rejection/ambiguous outcomes, atomic claim plus attempt numbering under concurrency, expired-lease and crash semantics, and explicit immutable context forwarding. That approval must explain how these semantics preserve current retry/DLQ/lease and business behavior; it does not authorize an outbox, runtime table, counter, fencing, or recovery/replay mechanism by implication. Re-open implementation only after that decision and interface exist. Source tests cannot prove deployed behavior, and no deployment/live smoke is in this scope.
