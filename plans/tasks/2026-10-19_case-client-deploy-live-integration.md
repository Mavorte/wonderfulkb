## Syntetické fixtures: nutné minimum bez dotyku existujících klientů

Plná přejímka potřebuje2aktivní,1inactive,1blocked klienta a více stránkovatelných cases; původní jeden klient/case nestačí. Pro tento konkrétní testovací task je dovoleno vytvořit nejvýše4nové syntetické client položky a12nových case položek na run. Client fixture provisioning proveď odděleně od business HTTP testů pomocí PutItem s `attribute_not_exists(client_id)` a unikátními validními UUID odvozenými od run_id, jasně syntetickými jmény/IČO dle OpenAPI. Pokud zvolené IČO už existuje, vyber jiné testovací, neoverwrite. Existujícím klientům neměň status ani metadata. Case vytvářet přes veřejný POST, ne přímým DB zápisem, kromě rollbacku nikdy neobcházej adaptér pro proof business chování. Žádný hromadný seed, delete ani nový endpoint, žádné změny tabulek/indexů. Fixture vytvoření je explicitní testovací provisioning, není to důkaz správného HTTP API. Ponechané syntetické IDs zapiš do sanitizovaného manifestu, úklid mimo tento task. Pokud role klientských nástrojů neumí podmíněný Put, reportuj AccessDenied bez eskalace rolí/credentials.

- Výchozí runner read-only; live write profil explicitní allow-writes a run_id. Ověř403bez/s chybným klíčem, JSON/error typy, IČO/name/status AND vyhledávání a normalizaci, case detail a client list,400neplatné query/limit/token,404chybějící entity. U tokenů respektuj skutečný veřejný kontrakt, nevymýšlej nový.
- POST bez case_id →201 a UUIDv4 přidělené službou, poté strong GET přes vrácenéID se shodnými poli/metadata včetně nested/decimal typů. Opakovaný totožný POST→další201 a jinéID; explicitně dodané case_id se ignoruje. Unknown klient404,inactive/blocked409 bez vytvoření case. Cases list newest-first, limit1→další stránka bez ztrát/duplicit, clients stránkování přes>1fixture, query-bound token test.
- Omezeně čekat na GSI propagaci s max60s deadline a budgetem, ne na POST/GET trvalost. Dva souběžné POST téhož aktivního klienta→201+201 a různá serverová UUID; oba ověřit přes GET. - POST není idempotentní: při nejednoznačném timeoutu jej automaticky neopakuj. Pokud je vrácenéID známé, ověř cíleným GET; jinak zaznamenej nejednoznačný výsledek a případnou kontrolu jen scoped syntetického klienta/run_id s bounded GSI budgetem, bez tvrzení že absence ihned dokazuje nezapsání. Nevyřešená nejistota→nonzero BLOCKED, žádné slepé retry. Missing fixtures/AccessDenied jsou nonzero NOT_READY/BLOCKED, ne green skip.

Ověřit key redakci i výjimky, no redirect, target/account guard, write opt-in, request budgets, rollback/revision/packing logiku a GSI timeout. Běžná unittest discovery nesmí nasazovat ani volat cloud. Nepřidávat cloud smoke do běžného registrovaného offline gate.

## Přejímka a důkazy

- Lokální stávající komponentové testy + nové offline testy, compileall, SAM validate --lint; zachovat `npm --prefix apps/backoffice test` a `npm --prefix apps/backoffice run build` a registrované brány. Neopravovat frontend mimo scope kvůli unrelated selhání; přesně reportovat.
- Sanitizované checkpointy: deployment manifest s account/region/function/URL/runtime/handler/build hash/CodeSha256 a časy, report všech povinných HTTP scénářů se statusy/výsledky/run_id/backendem a vytvořenými syntetickými IDs, přehled iterací a oprav + konečný proof, rollback metadata bez raw config/code/credentials. Získávej CodeSha256 také PO testech a ověř, že stále odpovídá testovanému artefaktu. API key hodnoty, klientské payloady, session tokens, presigned URL a raw SDK debug dumps nesmějí do verzovaných souborů/model výstupu.
- Success pouze pokud náš Python skutečně běží na původním endpointu, má DB backend bez fake fallbacku a všechny povinné live scénáře prošly, současně lokální brány/nezávislé review nezůstaly obejité. Stav kódu není runtime proof a samotný read-only subset není plná přejímka. Nové HTTP spojení nevynucuje jinou execution environment, toto netvrdit.
- Finální poznámka: co přesně bylo změněno v kódu/cloudu, příkazy bezpečně bez secretů, lokální i live výsledky, hash identity, počet deploy pokusů, ponechané fixture IDs a rollback umístění (bez obsahu). Pokud reálná přístupová hranice brání provedení, uvést konkrétní API/action/ARN a fail; žádný bypass nebo nepravdivé success.
