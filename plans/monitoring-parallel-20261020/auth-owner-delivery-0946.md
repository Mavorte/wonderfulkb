# Auth owner delivery input — 2026-10-20 09:46

## Decision
**Existing trusted caller→case/document authorization is not demonstrated in this repo slice. Do not enable monitoring GETs by reusing the shared intake API key or the Backoffice service API key. An implementation may proceed only by reusing an owner-approved trusted auth seam if one is supplied/located; absent that seam, the caller identity/role/case-entitlement policy requires explicit owner approval.** This is a precise security prerequisite, not a reason to build a new auth platform or another blocker document.

## Evidence and boundaries
- Proposal requires all monitoring reads to be case-authorized, explicitly including audit-only history when the present business object no longer exists; event presence must never imply entitlement. It expects integration with an existing case authorization owner, with no new business list/detail API. (`docs/proposals/proposal-20261019-150954-c8891f_monitoring-zpracovani-dokumentu-prubeh-mezivysledky-a-audit.md`, sections `source-contract`, `monitor-ui`, delivery and slice 1.)
- `be-intake/app/main.py` middleware validates `x-api-key` against global `API_KEY`; `require_case(case_id)` only validates ID syntax and existence in `wonderfulkb-uw-cases`. The intake middleware invokes it for upload path `/v1/cases/{case}/documents`; it does not map a human caller to a case. A service key authenticates the service, not caller entitlement.
- `be-intake/app/processing_monitor_lifecycle_routes.py` currently returns 403 `case read access unavailable` for runs/run/audit and documents this exact gap. No audit query occurs before authorization. Keep this deny-by-default behavior until a trusted policy seam is in hand.
- `apps/backoffice/functions/lib/awsApi.ts` documents a tenant-level secret `kb-aws-ingest-api-key` forwarded to AWS as `x-api-key`; it provides generic API transport only. Backoffice functions inspected contain no trusted-auth/case-permission implementation. Existing case UI/request paths do not establish an owner-side server authorization seam for this intake API.
- No `trustedauth` or `casepermissions` implementation was located under `apps/backoffice/functions` or this WonderfulKB checkout via bounded file/name search. Do not rely on UI/session role snapshots as server authorization.

## Smallest implementable reuse path (conditional)
If the auth owner supplies a real seam, have the existing App Runner FastAPI read boundary call that owner to establish a trusted principal and authorize the requested `(case_id, document_id)` before any audit-table read. The check must work for audit-only history (case entitlement independent of current document/analysis row), and confirm the document belongs to the requested case using an existing trusted identity owner. Carry no caller-supplied identity/role headers unless stripped at ingress and cryptographically/trusted-proxy asserted by the actual auth owner; the public shared `x-api-key` alone is insufficient. Keep responses private/no-store; fail closed on missing principal, mismatch, denied entitlement, or auth-owner outage (no fallback to existence/event lookup). Do not add artifact/content routes, new identities/roles, or change case-sharing policy.

Tests for a supplied seam: authorized principal + existing document succeeds; same principal denied another case; mismatched document/case denied; audit-only document history remains readable for an authorized case even when current business object is gone; unauthenticated/missing or forged identity denied; auth owner unavailable denied; assert audit store is not queried on all denials. Preserve no-store on all monitor responses. Then retain existing bounded paging/read-error tests and test actual HTTP route.

## Required owner decision if no seam exists
Name the trusted human/service principal source and the existing policy owner; specify how it derives case entitlement, how App Runner verifies/receives that identity (including trusted proxy/header boundary), and what authorization remains valid for audit-only history after business deletion. Do not let the implementation agent infer this from API-key possession, case existence, Backoffice UI role/session snapshot, or an audit event. No new policy/auth platform is authorized by current proposal.
