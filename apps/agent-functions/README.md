# Agent Functions

Wonderful Functions and tables used by the `case-evaluator` backoffice agent. The app has no UI. The agent's tools call the Functions with `context.functions.run("agent-functions/<slug>")`.

| Function | Body | Returns |
| --- | --- | --- |
| `eval-case-get` | `case_id` | Case and client (`openapi-case-client.yaml`). The client is found by listing clients, because `GET /clients/{id}` is not deployed. |
| `eval-documents-list` | `case_id` | Document list: id, title, label, processing status, page count. |
| `eval-document-get` | `case_id`, `document_id` | Document with its text split into numbered `pages`. |
| `eval-document-signatures` | `case_id`, `document_id` | Signatures detected in the document: `page`, `role`, `evidence` (the text next to the signature), `copy_suspicion`. Upstream: `GET .../documents/{id}/signatures?match_client=true&include_vectors=false`. |
| `eval-document-regions` | `case_id`, `document_id` | Regions of the document (labelled paragraphs and table rows of text-layer pages): `region_id` (`p{page}-r{nn}`), `page`, `label`, `party`, `refers_to`, `text`, `bbox` (0–1 of the page, top left), and `lines` (bbox plus character range in `text`) when there are several. `status` is `completed`, `not_run`, `failed` or `not_ready`; regions are empty unless `completed`. Fixtures are always `not_run`. Upstream: `GET .../documents/{id}/regions?include_geometry=true`. |

Errors come back as `{ error, message? }` with an HTTP status: `missing_parameter` (400), `case_not_found` / `document_not_found` (404), `upstream` (502).

## Live or mock

Each Function serves live data or mock data. Both modes return the upstream response shapes, so the same adapter code (`functions/shared/caseData.ts`) handles both.

| Name | Kind | Meaning |
| --- | --- | --- |
| `case_eval_aws_mock` | global | `true` serves every case from the mock layer. |
| `case_eval_documents_api_url` | global | Base URL of the AWS API (`wonderfulkb-agent-api`), which serves cases, clients and documents. |
| `kb-aws-ingest-api-key` | secret (API Key, `x-api-key`) | Key for that API. It accepts the ingest key. |

A Function uses mock data when any of these is true:
- the case ID has a fixture;
- `case_eval_aws_mock` is `true`;
- `case_eval_documents_api_url` is empty.

Fixture case IDs work even while live is on, so evals don't depend on AWS. An unknown case in mock mode returns 404.

## Tables

The case-evaluator writes these tables directly from its tools while it works. The backoffice app has them linked, so it can poll a case's evaluation live.

`agent_functions.case_evaluations` has one row per run. A re-run of a case adds a new row.

| Column | Meaning |
| --- | --- |
| `evaluation_id` | PK, e.g. `ev-mvfh...`. |
| `case_id` | |
| `status` | `running`, `completed` or `failed`. |
| `verdict` | `ready`, `needs_correction` or `needs_review`; set when the run completes. |
| `summary` | The agent's summary, or the failure reason. |
| `rules_total` | Number of rules the run will record. |
| `is_mock` | Whether fixture data was used. |
| `started_at`, `finished_at` | |

`agent_functions.case_evaluation_results` has one row per rule per run. The PK is `(evaluation_id, rule_id)`, and recording a rule again replaces its row.

| Column | Meaning |
| --- | --- |
| `case_id` | |
| `status` | `passed`, `missing`, `conflict`, `cannot_verify` or `not_applicable`. |
| `expected`, `found` | Short readable values. |
| `sources` | JSON `[{document_id, title, page, region_id?, bbox?, quote?, role?, issue?, anchor?}]`. The region fields locate a finding in the document; see the case-evaluator README. |
| `details` | Rule-specific JSON, e.g. the requirement → document mapping. |
| `reasoning` | The agent's explanation. |
| `recorded_at` | |

To follow a case, read the latest `case_evaluations` row for the `case_id` (by `started_at`), then its result rows. Progress is the number of result rows out of `rules_total`.

## Fixtures

`functions/shared/fixtures/` holds one file per case: the case, the client and the documents with their signatures, in upstream format.

| Case ID | Source | Notes |
| --- | --- | --- |
| `mock-solom-rec` | `solom_rec/` | Baseline case. |
| `mock-unhappy` | `unhappy_scenario/` | Defects listed in CONTEXT.md, e.g. borrower IČ `YYYYYYY`, a blank payment agreement. |
| `mock-stavby-fiser` | `stavby_fiser/` | Second real case: BOMAG roller from PWA s.r.o.; no invoice. |
| `mock-eval-*` | `eval-cases.json` | Synthetic eval cases, generated by the case-evaluator (see below). |

`eval-cases.json` holds the synthetic `mock-eval-*` cases that the case-evaluator's eval scenarios run against: a clean, fully compliant case (`mock-eval-clean`), and variants of it with one defect each, or a few chained. It is generated by the case-evaluator repo (`node eval-cases/build.ts <agent-functions checkout>`), which defines the cases and their answer keys; don't edit it by hand. Its cases list their documents by key into one shared `documents` table, because most of them reuse the clean case's documents.

A fixture can also simulate upstream trouble:
- `client: null`: the case's `client_id` has no client record, so `eval-case-get` returns `client: null`.
- `errors.list_documents` on the case, and `errors.get` / `errors.signatures` on a document: the documents API answers with that HTTP status, which the Functions report as `upstream` (502).

The real-case fixtures are regenerated from the PDFs with `scripts/build_fixtures.py <kb-hackathon folder>`, which needs `pypdf`. Some details:
- The client record is typed in from the `99_KK_systAPI.pdf` values. That PDF is not served as a document.
- Only the last two pages of the VOP are kept.
- Scanned pages (the orders, the handover protocols, the Stavby Fišer technical specification) get hand-written "OCR" text, typed in from the page images, in `scripts/fixture_extras.py`. Handwriting is marked "(ručně)", stamps "(razítko)", and parts hidden by the unhappy order's bug graphic "[nečitelné]".
- Blank pages stay empty: pages 3–4 of the unhappy handover protocol, and the unhappy payment agreement.
- `confidence` is 0.98 for digital PDFs. The typed-in scans have their own value: 0.55 for the unhappy order, 0.85–0.92 for the others.
- Signatures are typed in per document in `scripts/fixture_extras.py` as page, role and evidence. The roles are `provider` (SGEF), `borrower`, `supplier`, `guarantor` and `insurer`. The unhappy guarantee has only one SGEF signature, and its handover protocol and payment agreement have none.
